# English-first internationalization

English is the working default, including for browsers that prefer Chinese. Explicit `toolkit_locale` values `zh-CN`, `fr`, and `es` select Simplified Chinese, French, and Spanish for the storefront. Unknown values resolve to English. The root Next layout reads the cookie before rendering and supplies the same initial locale to the client provider, avoiding a Chinese/English hydration mismatch. Reading cookies makes these pages dynamic; do not cache a personalized-language HTML response as one public static page.

The header selector writes a one-year, same-site, host-only preference cookie and refreshes server content at the same URL; the provider and `html.lang` update together from the resolved server locale. HTTPS adds Secure. This is a preference, not an authentication cookie or secret. A new browser context has its own default. Browser-native validation dialogs may still follow the browser's own language settings.

## Commerce catalogs

`apps/web/content/shop.{en,zh-CN,fr,es}.json` own commerce messages, plurals and exact source-matched sample product translations. The server-only loader supplies just the selected dictionary to the context. Use `st` from `useLocale` in commerce UI, and `shopLocale` in server components. Use the lightweight `localizeShopError` for commerce errors so legacy workspace dictionaries are not duplicated in account/order bundles. Never translate authorization values, SKU identifiers or original user content. Changing language formats the same CNY amount; it does not convert currency or enable a market.

The old workspace and manual remain bilingual English/Chinese, falling back to English for French/Spanish. New merchant/admin systems, policy review, email modules and production product-translation workflows require their own implementation and acceptance; storefront coverage does not imply those systems exist. Cookie variants currently share the existing URLs; dedicated indexable language URLs/hreflang are not part of this increment.

## Portable core

`packages/i18n` exports Locale, resolveLocale, createTranslator, formatDate and formatNumber. It has no framework, database or authentication dependencies. Build it with `pnpm --filter @toolkit/i18n build`. Root postinstall builds it and root development runs its watcher. The web Docker build also builds it explicitly.

Each consuming product owns a catalog. The template uses English source strings as typed keys in apps/web/lib/messages.ts. The generic core also accepts semantic identifiers if a product needs context-specific meanings. Compile-time key matching prevents missing Chinese entries; runtime fallback preserves English when a translated value is empty. Named placeholders are plain text, including a numeric zero. Normal React escaping remains enabled. Never pass user content to an HTML insertion API.

The template provider and language selector live in apps/web/components/locale-provider.tsx. The independent InvoiceFlow adapter uses the same compiled core with its own catalog and React 18 provider. Copying a UI provider is framework glue; the locale/interpolation rules remain in the shared package.

## Add or change copy

1. Add the English key and Chinese translation to the app catalog; preserve every named placeholder in both editions.
2. Use t(key, values) for visible copy, accessible names and notifications. Keep product data as data. Do not translate role comparisons, project status values, HTTP field names, URLs or database identifiers.
3. Localize API errors by stable machine code. English retains the server's safe message; Chinese maps known codes to useful UI copy. Unknown codes fall back safely and request IDs remain intact. The API wire contract/logs stay English.
4. Use the shared Intl-based date/number helpers when formatting values for display. Stored timestamps and monetary values do not change when language changes.
5. Run package tests, web catalog/error tests and real browser locale journeys. Include an administrator in Chinese to catch accidental translation of authorization enum comparisons.

## Manuals

apps/web/content/manual.json is the single content source for `/manual` and both Markdown editions. After editing it, run `node scripts/generate-manual.mjs` and format the generated docs. Keep section IDs aligned across languages. The manual documents current behavior and limitations, not planned features.

## Existing-product boundary

Do not replace another product's authentication cookies, user table, tenant identifiers or role model just to reuse translations. The InvoiceFlow pilot keeps NestJS/Prisma 5 and its existing organization isolation; the template keeps Fastify/Prisma 6 and personal project ownership. This iteration does not provide multilingual SEO URL routing, translation management SaaS, machine translation, regional time-zone policy or cross-product SSO.
