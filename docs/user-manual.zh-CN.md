# 用户操作与项目接入手册

fullstack-toolkit 是可复用的工程底座，并带有可操作的私人项目示例。英语为默认工作语言，可通过语言选择器切换简体中文。接入后的产品各自保留域名、数据、凭据与权限模型；它不是所有产品共用的统一登录服务。

## 1. 创建账号与登录

1. 打开工作空间首页，在“创建账号”下填写姓名、有效邮箱和 12–128 个字符的独立密码，然后提交。注册后以普通用户 USER 身份登录。

2. 已有账号请选择“登录”，使用原邮箱和密码。密码错误会显示提示；需要联系操作者时，请保留请求编号。

3. 会话最长有效七天。使用完毕后请退出登录，尤其是在共用设备上。退出会在服务端撤销当前会话；仅关闭浏览器标签页不会撤销会话。

4. 当前没有邮箱验证与找回密码流程。不要复用重要账号的密码；在保存重要数据之前，先与产品操作者确认恢复办法。

## 2. 管理私人项目

1. 点击“+ 新建项目”，填写 1–120 个字符的名称、最多 2000 个字符的可选描述及状态，然后点击“创建项目”。卡片会出现在计划中、进行中或已完成栏目。

2. 点击卡片上的“编辑”修改名称、描述或状态，保存后刷新确认数据仍然存在。“取消”只关闭表单，不保存修改。

3. 搜索框对已加载项目的名称和描述进行筛选。页面最多显示最近 100 个项目；概览统计也是这些已加载项目的统计，并非无限量报表。

4. 点击“删除”并在浏览器确认框中确认。应用内没有回收站，删除不可撤销；取消确认则保留项目。

5. 项目归创建账号所有。其他账号即使知道项目 ID，也不能查询、修改或删除。本示例不提供项目共享或组织成员功能。

## 3. 使用英语或简体中文

1. 在顶部语言选择器中选择 English 或简体中文。新访客始终默认使用英语，不跟随浏览器语言自动改为中文。

2. 语言选择保存为有效一年的非敏感偏好 Cookie，刷新和进入手册页后仍会恢复。切换语言不改变账号、会话、项目 ID 或访问权限。

3. 界面文案、表单标签、状态名称、通知、已知 API 错误码对应的提示与日期格式会切换语言。项目名称、描述等用户内容不会被自动翻译。

4. API 字段、枚举值、错误码、请求编号、日志和代码标识符保持英语。新产品可复用 @toolkit/i18n，并维护自己的业务词典。

## 4. 管理员权限

1. 新账号一律为 USER。没有公开默认管理员、注册时选择角色或浏览器中提升角色的功能。

2. 经操作者显式配置的 ADMIN 可在侧栏打开“成员”，查看最近 100 位成员，再返回项目。该页面仅为目录，不是修改用户或角色的管理后台。

3. 操作者在私有环境中明确设置 ADMIN_EMAIL 与 16–128 个字符的独立 ADMIN_PASSWORD，再运行 pnpm db:seed 创建新管理员。已有账号不会被覆盖。配置完成后移除引导变量，禁止将凭据写入源码、CI 日志或工单。

4. 普通用户无法访问成员目录 API。隐藏菜单只是展示，真正的角色检查在 API 服务端执行。

## 5. 开始下一个项目

1. 从模板源码创建一份新副本，保留原项目文件、数据库与部署。安装 Node 22.14+ 和 package.json 锁定的 pnpm，将 .env.example 复制为私有 .env。

2. 运行 node scripts/init-project.mjs my-product、pnpm install --frozen-lockfile、pnpm db:migrate，然后 pnpm dev。初始化器只修改根名称/README 标题并在缺失时创建 .env，不创建远程仓库。

3. 已有数据库必须按 docs/deployment.md 先备份并核实迁移基线。不要 reset 数据库、把生产数据库复制进模板，或为旧用户凭空生成密码。

4. 通过迁移、共享 API 契约和服务端授权添加业务字段。可参考项目示例的完整链路；已有产品的租户/角色规则应保留，不能用示例中更简单的个人归属模型替换。

5. 执行 format:check、lint、typecheck、test、build、size-check 和 e2e。使用可丢弃测试数据库与账号；E2E 会创建数据，禁止误连客户环境。扩展细节见 docs/reuse.md 和 docs/i18n.md。

## 6. 部署与运维

1. 每个项目使用独立 HTTPS Origin、Compose 项目名、数据卷、宿主机端口和私有环境。复制其他项目的凭据或复用其数据卷，不属于基础设施复用。

2. 设置 APP_ORIGIN 为精确的 HTTPS Origin，执行 docker compose --env-file /secure/runtime.env -f docker/docker-compose.yml up -d --build。共用服务器上要先选择未占用的回环端口、独立 Compose 名称与目录，只配置新域名的代理。

3. 本版本使用 SQLite 单实例。/api/health 检查进程存活，/api/ready 查询数据库。健康检查为绿，不代表登录、权限与业务已经验证。

4. 迁移前停掉本项目写入进程并备份完整数据卷，在独立临时卷中验证恢复。重要备份应异地保存并设置保留策略。线上禁止执行 compose down -v。

5. 保留不可变源码/镜像及每个发布版本的环境文件。仅在兼容数据库结构时回滚代码；结构恢复需要已验证备份和对应应用版本。见 docs/deployment.md 与 docs/verification.md。GitHub 工作流还需要真实仓库、Secrets 和 Environment 策略才能运行。

## 7. 排错与能力边界

1. API 不可用时检查网络、API/ready、运行环境和代理路由。不要关闭 TLS 校验或公开数据库来消除红色提示。

2. 401：重新登录。403：检查角色以及 Origin/CSRF 配置。其他账号的项目返回 404 是预期行为。409 通常表示记录重复；429 表示请求过于频繁，请稍后重试。

3. 报错时提供页面/操作、时间、请求编号与预期结果。不要发送密码、Cookie、令牌、环境文件或客户文档。

4. 当前不提供找回密码、跨产品 SSO、团队项目共享、在线订阅、多机高可用、PostgreSQL 多副本、可用性保证或自动异地备份。InvoiceFlow 试点在本地隔离环境验证复用，不会悄悄迁移现有 InvoiceFlow 生产服务。
